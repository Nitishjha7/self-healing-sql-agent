# Evaluation Results

Model: `gemini-3.5-flash-lite` · 20 questions · execution accuracy
(metric defined in [README.md](README.md))

Three conditions, differing only in the schema description handed to the LLM. The
questions, the database, and the agent code are identical across all three.

---

## Headline

| Condition | Retries off | Retries on | Delta | Avg retries (on) |
|---|---|---|---|---|
| **Production schema** (hand-tuned) | 95% | 95% | **+0pp** | 0.00 |
| **Degraded schema** (bare column list) | 90% | 90% | **+0pp** | 0.00 |
| **Stale schema** (wrong column names) | 15% | **30%** | **+15pp** | 2.25 |

**The self-healing loop doubles accuracy — but only when queries actually fail.**
In the two conditions where generation never produced a database error, the loop
never ran and contributed exactly nothing. That is not a disappointing result; it
is the result, and it locates precisely where the architecture earns its cost.

---

## Run 1 — production schema description

The hand-tuned `get_schema_description()`: example values, an explicit
`employees.department_id -> departments.id` relationship line, and a direct
statement that a join is mandatory.

| MAX_RETRIES | Accuracy | Strict | Avg retries | Healed |
|---|---|---|---|---|
| 0 | 19/20 (95%) | 16/20 (80%) | 0.00 | 0 |
| 3 | 19/20 (95%) | 17/20 (85%) | 0.00 | 0 |

`Avg retries = 0.00` is the whole story: **the loop never fired.** Not once in 20
questions did the model produce SQL that Postgres rejected. With a description
that names the join key and states outright that `employees` has no
department-name column, generation simply does not make schema mistakes on a
two-table schema.

So this run measures the **prompt**, not the **architecture**.

The single failure — question 18, *"For each department, what percentage of its
budget goes to salaries?"* — is instructive because retrying could not have saved
it:

```sql
-- agent
SELECT d.name FROM departments d JOIN employees e ON d.id = e.department_id
GROUP BY d.id, d.name ORDER BY SUM(e.salary) ASC LIMIT 1
```

Valid SQL. Executes cleanly. Answers a *different question* — lowest-spending
department instead of a per-department percentage. This is a **semantic** failure,
and the loop is structurally blind to it: the loop is driven by database
exceptions, and there is no exception here.

The strict-vs-relaxed gap (80% vs 85%) is the projection issue the two-metric
design exists for — several correct answers returned extra columns.

## Run 2 — degraded schema description

A bare column listing: no relationship line, no example values, no join warning.
What a description looks like when generated by introspection rather than
hand-tuned.

| MAX_RETRIES | Accuracy | Strict | Avg retries | Healed |
|---|---|---|---|---|
| 0 | 18/20 (90%) | — | 0.00 | 0 |
| 3 | 18/20 (90%) | — | 0.00 | 0 |

Accuracy dropped 5pp, and again the loop never fired. The extra failure was
question 14, *"Which employees have a manager role?"* — without example values
the model guessed at how roles are spelled. `WHERE role = 'Manager'` executes
fine and returns zero rows. Wrong answer, no exception, nothing to heal.

**This run taught us something the design did not anticipate:** removing schema
*guidance* produces semantically wrong queries, not failing ones. To exercise the
loop you need a schema description that is not merely thin but *incorrect*.

## Run 3 — stale schema description

Column names that no longer exist — `emp_name` instead of `name`, `dept_id`
instead of `department_id`, `job_title` instead of `role`, `city` instead of
`location`. This is **schema drift**: the docs describe a shape the migration
already changed. It is one of the most common ways a real Text-to-SQL deployment
breaks, and unlike Run 2 it produces genuine execution errors.

| MAX_RETRIES | Accuracy | Strict | Avg retries | Healed |
|---|---|---|---|---|
| 0 | 3/20 (15%) | 3/20 (15%) | 0.85 | 0 |
| 3 | **6/20 (30%)** | 6/20 (30%) | 2.25 | **3** |

**Accuracy doubled.** Questions 3, 5 and 16 failed on the first attempt and were
repaired by the loop reading the Postgres error — which carries a `HINT:` naming
the real column:

```
column "emp_name" does not exist
HINT:  Perhaps you meant to reference the column "employees.name".
```

That hint is exactly the feedback the retry prompt is built to consume, and it is
why error-informed regeneration beats blind resampling: the model is not asked to
guess again, it is handed the correction.

### Why only 30%, honestly

Three attempts is not enough when *every* column name is wrong. Postgres hints
one column at a time, so a query referencing three bad columns needs several
rounds, and the budget runs out — visible in `avg retries = 2.25`, close to the
ceiling of 3. This condition is deliberately brutal; real schema drift usually
affects one or two columns, where the loop would recover most of the way.

---

## What this eval supports, and what it does not

**Supported:** the loop's value is a direct function of how often generation
produces *executable-but-invalid* SQL. Where that rate is zero, the loop is dead
weight; where it is high, it doubles accuracy.

**Supported:** the loop only addresses **execution** failures. Both no-delta runs
failed on semantic errors — valid SQL answering the wrong question — which a
mechanism keyed on database exceptions cannot detect by construction. Catching
those needs a different mechanism (an LLM critic validating the result against
the question, or self-consistency across sampled queries).

**Supported:** prompt quality and architectural resilience are substitutes at
this scale. A well-tuned schema description got 95% with no loop at all. That is
worth knowing before adding machinery.

**Not supported:** any general claim that self-healing improves Text-to-SQL
accuracy. It improved it here, in one condition, on a two-table schema, with one
model, over 20 questions. That is a direction, not a proof.

## Reproducing

```bash
docker compose up -d db

# Run 1
docker compose run --rm --no-deps -e GEMINI_MODEL=gemini-3.5-flash-lite \
  -v "$PWD/eval:/app/eval" backend python -m eval.run_eval

# Run 2
... python -m eval.run_eval --degrade-schema --out eval/results_degraded.json

# Run 3
... python -m eval.run_eval --stale-schema --out eval/results_stale.json
```

Per-question output is in `results.json`, `results_degraded.json`,
`results_stale.json`.
