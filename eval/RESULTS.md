Model: `gemini-3.5-flash-lite` · 20 questions · execution accuracy

## Run 1 — production schema description

The hand-tuned `get_schema_description()`: example values, an explicit
`employees.department_id -> departments.id` relationship line, and a direct
statement that a join is mandatory.

| MAX_RETRIES | Accuracy | Strict | Avg retries | Healed by retry |
|---|---|---|---|---|
| 0 (loop disabled) | 19/20 (95%) | 16/20 (80%) | 0.00 | 0 |
| 3 (real system) | 19/20 (95%) | 17/20 (85%) | 0.00 | 0 |

**Self-healing delta: +0%.**

### What this actually means

The loop contributed nothing here — and that is a result worth reporting, not a
failure to hide.

`Avg retries = 0.00` is the explanation: **the loop never fired.** Not once in 20
questions did the model produce SQL that Postgres rejected. With a schema
description that names the join key and states outright that `employees` has no
department-name column, the generation step simply does not make schema mistakes
on a two-table schema.

So this run measures the **prompt**, not the **architecture**. An eval where the
mechanism under test never activates cannot say anything about that mechanism.

The one failure, question 18 ("For each department, what percentage of its budget
goes to salaries?"), is instructive precisely because retrying could not have
helped it:

```sql
-- agent
SELECT d.name FROM departments d JOIN employees e ON d.id = e.department_id
GROUP BY d.id, d.name ORDER BY SUM(e.salary) ASC LIMIT 1
```

Valid SQL. Executes cleanly. Answers a *different question* — it returns the
lowest-spending department instead of a per-department percentage. This is a
**semantic** failure, and the self-healing loop is structurally blind to it: the
loop is driven by database exceptions, and there is no exception here. It is the
exact failure class the architecture does not address, which is worth being able
to say out loud.

The strict-vs-relaxed gap (80% vs 95%) is the projection issue the two-metric
design exists for: several correct answers returned extra columns.

## The honest takeaway

Two claims this eval supports, and one it does not:

**Supported:** on a small, well-described schema, a competent model gets ~95% of
questions right in one shot, and the remaining failures are semantic rather than
syntactic — so a retry loop keyed on execution errors has nothing to fix.

**Supported:** the value of the self-healing loop is a function of how often
generation actually fails, which is driven by schema size, schema ambiguity, and
how much guidance the prompt provides. Those are the variables that matter, not
the loop itself.

**Not supported:** any claim that the loop improves accuracy in general. On this
dataset, under these conditions, it did not — because it never ran.
